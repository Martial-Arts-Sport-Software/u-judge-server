# U'Judge System: описание проекта

Статус документа: рабочая спецификация U'Judge v1 Pilot.

Дата фиксации: 30 августа 2026 года.

## 1. Назначение

U'Judge System - локальная клиент-серверная система электронного судейства соревнований по хапкидо. Система должна работать в изолированной Wi-Fi/LAN-сети без доступа в интернет и объединять:

- мобильные пульты боковых судей на Android и iPhone;
- desktop-приложения площадок на Windows и macOS;
- импорт турнирных сеток и управление ходом соревнования;
- расчёт результатов по правилам Федерации Хапкидо России;
- один desktop peer на одну площадку, обслуживающий 5-7 мобильных судей через выделенный Wi-Fi роутер;
- аудит судейских событий, историю, экспорт и резервное копирование.

Первый релиз определяется как пилотная версия для полевого испытания. Это не production-релиз и не декларация готовности к официальному применению без отдельной экспертной приёмки.

## 4. Термины

| Термин            | Значение                                                                                     |
|-------------------|----------------------------------------------------------------------------------------------|
| Соревнование      | Общая сущность турнира, объединяющая участников, категории, сетки, площадки и результаты     |
| Площадка          | Один корт/додянг и обслуживающий его desktop-peer                                            |
| Peer              | Равноправный экземпляр U'Judge Server, хранящий полную копию состояния соревнования          |
| Сетка             | Импортированная последовательность поединков или выступлений одной категории                 |
| Владелец сетки    | Единственная площадка, имеющая право создавать события для назначенной ей сетки              |
| Поединок          | Соревновательная единица Kerugi или Tanbon между двумя участниками                           |
| Выступление       | Соревновательная единица технической дисциплины                                              |
| Судейское событие | Неизменяемая запись о балле, штрафе, оценке, состоянии раунда или операторской корректировке |
| Проекция          | Текущее состояние, рассчитанное из журнала событий и сохранённое в PostgreSQL                |
| Клиент            | Мобильное приложение судьи                                                                   |
| Оператор/арбитр   | Совмещённая роль пользователя desktop-приложения площадки                                    |
| Наблюдатель       | Пользователь полноэкранного режима табло без прав изменения                                  |

## 5. Пользователи и роли

### 5.1. Оператор/арбитр площадки

Совмещённая роль отвечает за подготовку и проведение соревнования на одной площадке:

- присоединяет peer к соревнованию по коду;
- импортирует или получает сетки от других peers;
- назначает сетки площадке;
- подтверждает мобильные устройства и судей;
- запускает и останавливает раунды;
- вводит решения рефери, штрафы и корректировки;
- контролирует состояние соединений;
- завершает поединки и выступления;
- просматривает аудит и формирует экспорт.

### 5.2. Боковой судья

Работает с мобильным клиентом. Судья указывает фамилию, подключается к площадке и использует выбранную дисциплину. Для Kerugi и Tanbon события отправляются немедленно. Для технических дисциплин итоговая оценка отправляется после завершения выставления критериев.

### 5.3. Наблюдатель

Получает актуальное состояние поединка в режиме только для чтения: участников, счёт, штрафы, таймер, раунд, площадку и следующий поединок.

## 7. Текущее состояние

Исходной точкой документации являются локальные feature-ветки и текущие рабочие деревья:

- клиент: `feat/server-connection`;
- сервер: `feat/client-connection`.

Публичные ветки `main` отстают от локальной разработки.

### 7.1. Реализовано в server

- Kotlin/JVM desktop-проект с модулями `desktop` и `server`;
- Compose Desktop shell и навигация между стартовым экраном и экраном устройств;
- ввод фамилии и переключение русского/английского языка;
- встроенный Ktor CIO server на `0.0.0.0:8080`;
- `GET /` и заглушка `POST /score`;
- публикация `_u-judge._tcp` через mDNS;
- ручной workflow сборки installers для Windows, macOS и Linux.
- CI на `push` и `pull_request`: Gradle Wrapper validation, whitespace check и Gradle build на Java 21.

### 7.2. Не реализовано в server

- модель соревнования и сеток;
- pairing и реестр подключённых устройств;
- рабочий сетевой контракт оценок;
- таймер, scoring и формулы дисциплин;
- managed PostgreSQL provisioning, реальный lifecycle и clean-machine proof; durable journal migration и process
  supervision существуют только как Stage 1 JDBC spike;
- P2P-обнаружение, авторизация и репликация;
- импорт XLSX, история, аудит, экспорт и backup;
- интерфейсы арбитра, наблюдателя и редактора сеток;
- автоматические тестовые сценарии.

Текущее `POST /score` не читает тело запроса и всегда отвечает `Score OK`. Оно не является API v1.

## 8. Целевая архитектура v1 Pilot

```text
Mobile clients                         Mobile clients
      | mDNS + HTTP/WebSocket                |
      v                                      v
+----------------------+    P2P    +----------------------+
| Desktop peer: Court 1|<---------->| Desktop peer: Court 2|
| Compose Desktop      |            | Compose Desktop      |
| Application services|            | Application services|
| Event journal        |            | Event journal        |
| Local PostgreSQL     |            | Local PostgreSQL     |
+----------------------+            +----------------------+
           ^                                  ^
           +------ replicated competition ----+
                         state
```

### 8.1. Границы компонентов

| Компонент          | Ответственность                                                     |
|--------------------|---------------------------------------------------------------------|
| Desktop UI         | Управление площадкой, сетками, устройствами, поединком, отчётностью |
| Client API         | Pairing, команды, итоговые оценки, история и экспорт                |
| Realtime gateway   | WebSocket-события, ACK, heartbeat, reconnect и актуальное состояние |
| Scoring engine     | Проверка событий и расчёт результата по дисциплине                  |
| Event journal      | Неизменяемые события с глобально уникальными ID                     |
| Projection store   | PostgreSQL-проекции состояния соревнования                          |
| Peer discovery     | Обнаружение peers в LAN и присоединение по коду соревнования        |
| Replication engine | Обмен диапазонами событий, дедупликация и контроль сходимости       |
| Backup/export      | Автоснимки, XLSX и CSV                                              |

### 8.2. Владение данными

- Каждый peer хранит полную реплику состояния соревнования.
- Каждая сетка один раз назначается площадке и не передаётся в рамках v1 Pilot.
- Только peer-владелец создаёт события поединков и выступлений своей сетки.
- События имеют неизменяемый ID, ID peer, ID соревнования, ID сетки, локальную последовательность, время и payload.
- Общим источником истины является сходящееся объединение валидных журналов всех peers.
- PostgreSQL хранит журнал и проекции, но синхронизация выполняется на прикладном уровне, а не репликацией таблиц.
- После восстановления связи peers обмениваются отсутствующими событиями и повторно строят проекции.

Конкретный алгоритм anti-entropy, обнаружения пропусков и криптографической проверки выбирается отдельным ADR после технического прототипа. Kafka не зафиксирована как обязательная технология.

### 8.3. Сетевой контракт

- mDNS используется для обнаружения сервера клиентами и peers друг другом.
- HTTP используется для pairing, импорта, конфигурации и запросов истории.
- WebSocket используется для realtime-событий, состояния сессии, heartbeat и reconnect.
- Все изменяющие команды имеют уникальный idempotency key.
- Клиентские события подтверждаются ACK и безопасно повторяются после reconnect.
- Код соревнования используется для присоединения нового peer; мобильное устройство отдельно подтверждается оператором.

## 9. Основные сценарии

### 9.1. Подготовка соревнования

1. Первый peer создаёт соревнование и код присоединения.
2. Остальные площадки обнаруживают peers и присоединяются по коду.
3. Оператор импортирует готовые сетки из `df.xlsx`.
4. Desktop сохраняет импортированные сущности соревнования в БД и формирует `PDF 1` для печати.
5. Сетки навсегда назначаются площадкам.
6. Операторы проверяют участников, порядок и preview сетки.
7. После обработки сеток desktop формирует `PDF 2` с результатами.

### 9.2. Подключение судьи

1. Судья вводит фамилию на мобильном клиенте.
2. Клиент обнаруживает `_u-judge._tcp` и выбирает площадку.
3. Оператор видит запрос и подтверждает устройство.
4. Судья выбирает дисциплину и при необходимости категорию.
5. Сервер сообщает номер и состояние текущего поединка/выступления.

### 9.3. Kerugi

1. Оператор открывает очередной поединок и проверяет состав судей.
2. Таймер и состояние раунда передаются клиентам и watcher-экрану.
3. Клиенты немедленно отправляют события ударов.
4. Scoring engine засчитывает балл при выполнении настраиваемого кворума внутри настраиваемого окна, по умолчанию `1000 мс`.
5. Оператор вводит броски, вращения, Gamjeom, нокдауны и корректировки.
6. Все исходные и производные события сохраняются в аудите.
7. По завершении результат фиксируется в сетке и реплицируется peers.

### 9.4. Техническое выступление

1. Оператор открывает выступление и проверяет состав судей.
2. Судьи выставляют критерии локально в течение выступления.
3. `Send` передаёт окончательную оценку; повторное редактирование судьёй запрещено.
4. Сервер ожидает настроенное число оценок или явное решение оператора.
5. Настраиваемая формула по умолчанию исключает минимум и максимум, а оставшиеся оценки усредняет.
6. Итог и исходные оценки сохраняются и реплицируются.

### 9.5. Сетевое разделение

1. Площадка продолжает работу со своими сетками и локальными клиентами.
2. Клиент при потере связи буферизует неподтверждённые события.
3. Peer сохраняет события в локальном PostgreSQL.
4. После reconnect команды повторяются с теми же ID и дедуплицируются.
5. Peer-события обмениваются до сходимости общего состояния.

## 11. Ограничения v1 Pilot

- Один разработчик и целевой срок до 12 недель.
- Один desktop peer на одну площадку и 5-7 мобильных клиентов через выделенный Wi-Fi роутер.
- До 500 участников в одном соревновании.
- Windows 11 и macOS Ventura/Sonoma/Tahoe для server; Honor 50 Lite на Android 11 и iPhone 15 на iOS 26.6 для client.
- Готовые сетки импортируются; генерация жеребьёвки не входит в пилот.
- Подпись Windows installer и notarization macOS переносятся после пилота.
- Публичная публикация приложений в магазинах не требуется; используются APK и TestFlight.
