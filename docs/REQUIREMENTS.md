# U'Judge System: функциональные требования

Статус документа: baseline требований U'Judge v1 Pilot.

Дата фиксации: 30 августа 2026 года.

## 1. Правила ведения требований

Приоритеты:

| Приоритет | Значение                                                               |
|-----------|------------------------------------------------------------------------|
| Must      | Без требования пилот не допускается к полевому испытанию               |
| Should    | Требование ожидается в пилоте, но может быть перенесено явным решением |
| Could     | Допустимое улучшение после прохождения Must-гейтов                     |

Статусы:

| Статус      | Значение                          |
|-------------|-----------------------------------|
| Implemented | Реализовано и проверено           |
| Partial     | Реализована только часть сценария |
| Planned     | Подтверждено для v1 Pilot         |
| Blocked     | Требуются данные или решение      |

Если текущий код расходится с этим документом, требования описывают целевое поведение v1 Pilot, а расхождение считается
задачей roadmap.

## 2. Системные требования

| ID      | Приоритет | Требование                                                                | Критерий приёмки                                                                                |
|---------|-----------|---------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| SYS-001 | Must      | Система работает без доступа в интернет в изолированной LAN               | Подготовка, судейство, синхронизация, история и экспорт проходят при отключённом WAN            |
| SYS-002 | Must      | Одно соревнование поддерживает до 8 площадок                              | В нагрузочном тесте 8 peers обмениваются состоянием без потерь и дублей                         |
| SYS-003 | Must      | Система поддерживает до 500 участников                                    | Импорт, навигация, расчёт и экспорт проходят на тестовом наборе из 500 участников               |
| SYS-004 | Must      | Интерфейс доступен на русском и английском                                | Все пользовательские строки переключаются без перезапуска; fallback явно определён              |
| SYS-005 | Must      | Сервер поддерживает Windows и macOS                                       | Приложение устанавливается и запускается на чистых целевых системах                             |
| SYS-006 | Must      | Клиент поддерживает Android и iPhone                                      | Pilot build устанавливается через APK и TestFlight на реальных устройствах                      |
| SYS-007 | Must      | Каждое изменяющее действие аудируется                                     | По результату можно определить соревнование, сетку, поединок, автора, источник, время и payload |
| SYS-008 | Must      | Все идентификаторы сущностей стабильны и глобально уникальны              | Повторная доставка события не создаёт дубль                                                     |
| SYS-009 | Must      | Время и порядок событий не зависят только от wall clock одного устройства | Контракт содержит sequence/логический порядок и учитывает clock offset клиентов                 |

## 3. Соревнование и площадки

| ID      | Приоритет | Требование                                                  | Критерий приёмки                                                                  |
|---------|-----------|-------------------------------------------------------------|-----------------------------------------------------------------------------------|
| CMP-001 | Must      | Оператор может создать соревнование                         | Создаются уникальный ID, настройки и код присоединения                            |
| CMP-002 | Must      | Новый peer присоединяется по коду соревнования              | Неверный/просроченный код отклоняется, успешный peer получает состояние           |
| CMP-003 | Must      | Оператор видит список peers и их состояние                  | Для каждого peer видны ID, площадка, last seen и статус синхронизации             |
| CMP-004 | Must      | Peer может переименовать только локальную площадку          | Изменение реплицируется и не меняет идентификатор peer                            |
| CMP-005 | Must      | Сетка назначается ровно одной площадке                      | Два peers не могут стать владельцами одной сетки                                  |
| CMP-006 | Must      | Назначение сетки неизменно после подтверждения              | UI не предоставляет передачу; конфликтующая команда отклоняется                   |
| CMP-007 | Must      | Peer продолжает свои сетки при потере связи с другими peers | Локальное судейство не блокируется, состояние отмечается как несинхронизированное |
| CMP-008 | Should    | Оператор видит прогресс всех сеток                          | После сходимости отображаются актуальные стадии и результаты всех площадок        |

`IMP-001` остаётся blocked до получения реального XLSX.

## 7. Kerugi

Нормативная основа: раздел 4.1 правил ФХР 2023.

| ID      | Приоритет | Требование                                                        | Критерий приёмки                                                                    |
|---------|-----------|-------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| KER-001 | Must      | Server поддерживает 2 или 3 боковых судьи и настраиваемый состав  | Настройка сохраняется до старта и применяется scoring engine                        |
| KER-002 | Must      | Кворум событий настраивается                                      | По умолчанию при 3 судьях балл требует минимум 2 подтверждения                      |
| KER-003 | Must      | Окно совпадения настраивается                                     | Значение по умолчанию `1000 мс`, новое значение применяется только к новым событиям |
| KER-004 | Must      | Боковой судья отправляет участника и область `HEAD`/`BODY`        | Невалидный цвет или область отклоняются                                             |
| KER-005 | Must      | Баллы ударов рассчитываются по правилам                           | Туловище даёт `1`, голова `2`; для одного участника конфликтующие score candidates в окне `KER-003` дают минимальную оценку; дополнительные решения вводятся оператором |
| KER-006 | Must      | Оператор вводит броски и дополнительный балл за вращение          | Событие содержит тип, участника, значение и автора                                  |
| KER-007 | Must      | Оператор вводит Gamjeom                                           | Штраф увеличивает счёт соперника и сохраняется отдельно                             |
| KER-008 | Must      | Server поддерживает отмену/коррекцию балла                        | Создаётся компенсирующее событие; исходная запись не удаляется                      |
| KER-009 | Must      | Все события, включая не образовавшие балл, доступны аудиту        | Можно объяснить, почему конкретное нажатие было/не было засчитано                   |
| KER-010 | Must      | Server ведёт два основных раунда и дополнительный раунд           | Длительность зависит от возрастной категории по правилам                            |
| KER-011 | Must      | Таймер поддерживает start, pause, resume и stop                   | Состояние восстанавливается после перезапуска из persisted events                   |
| KER-012 | Must      | Перерыв между раундами учитывается отдельно                       | Watcher и оператор видят оставшееся время и тип периода                             |
| KER-013 | Must      | Поддерживается победа по финальному счёту и golden round          | Причина победы сохраняется в результате                                             |
| KER-014 | Should    | Поддерживаются остальные нормативные причины победы               | PОР, РБ, СС, ДИКВ и другие причины доступны оператору                               |
| KER-015 | Must      | При достижении 10 Gamjeom система предупреждает о дисквалификации | Автоматическое решение требует подтверждения оператора                              |

## 8. Tanbon

Tanbon в v1 является пользовательской дисциплиной U'Judge и требует экспертного подтверждения перед полевым пилотом.

| ID      | Приоритет | Требование                                       | Критерий приёмки                                          |
|---------|-----------|--------------------------------------------------|-----------------------------------------------------------|
| TAN-001 | Must      | Сценарий realtime и кворума соответствует Kerugi | Применяются настроенные judge count, quorum и window      |
| TAN-002 | Must      | Удар в голову даёт `2` балла                     | Событие корректно меняет счёт выбранного участника        |
| TAN-003 | Must      | Удар в туловище даёт `1` балл                    | Событие корректно меняет счёт выбранного участника        |
| TAN-004 | Must      | Центральная кнопка отправляет `CROSS`            | Событие хранится в аудите и не изменяет счёт              |
| TAN-005 | Must      | UI и API различают Tanbon и Kerugi               | Событие одной дисциплины нельзя применить к сессии другой |

## 9. Технические дисциплины

| TEC-008 | Must      | `Send` фиксирует окончательную оценку                                | Повторная оценка судьи для того же выступления отклоняется           |
| TEC-009 | Must      | Server сохраняет исходные критерии, а не только сумму                | История позволяет восстановить расчёт                                |

| TEC-011 | Must      | Формула по умолчанию исключает min/max и усредняет оставшиеся оценки | При пяти оценках среднее считается по трём оставшимся                |
| TEC-012 | Must      | При нестандартном числе судей формула явно показывает делитель       | Итог воспроизводим из настроек и исходных оценок                     |
| TEC-013 | Must      | Tie-break определяется правилами дисциплины                          | Hosinsool приоритет техники; freestyle приоритет презентации         |
| TEC-014 | Must      | Оператор видит submitted/pending по каждому судье                    | Итог не фиксируется незаметно при недостающей оценке                 |

## 11. P2P и сходимость

| ID      | Приоритет | Требование                                                  | Критерий приёмки                                                                       |
|---------|-----------|-------------------------------------------------------------|----------------------------------------------------------------------------------------|
| P2P-001 | Must      | Все peers равноправны и не требуют центрального coordinator | Выключение любого peer не останавливает остальные площадки                             |
| P2P-002 | Must      | Каждый peer хранит полную копию журнала соревнования        | После полной синхронизации набор event IDs одинаков на всех peers                      |
| P2P-003 | Must      | События реплицируются at-least-once с дедупликацией         | Повторная доставка не меняет результат второй раз                                      |
| P2P-004 | Must      | Peer обнаруживает отсутствующие диапазоны                   | После reconnect автоматически запрашиваются пропущенные события                        |
| P2P-005 | Must      | Порядок событий одного владельца детерминирован             | Sequence gap не применяется незаметно; peer ожидает или запрашивает пропуск            |
| P2P-006 | Must      | Событие проверяется на авторство владельца сетки            | Событие чужого peer не меняет сетку                                                    |
| P2P-007 | Must      | Partition не приводит к конфликту владения                  | Сетка не может быть передана или переназначена offline                                 |
| P2P-008 | Must      | Сходимость проверяется диагностически                       | UI показывает lag, missing count и время последней успешной синхронизации              |
| P2P-009 | Must      | Присоединение требует competition code                      | Неавторизованный peer не получает персональные и турнирные данные                      |
| P2P-010 | Must      | Peer после перезапуска продолжает репликацию                | Durable cursor/sequence восстанавливаются из PostgreSQL                                |
| P2P-011 | Must      | Механизм проходит тест длительного partition                | После накопления событий на двух площадках итоговые журналы сходятся без ручной правки |

## 12. Клиентская доставка и reconnect

| ID      | Приоритет | Требование                                                                  | Критерий приёмки                                                        |
|---------|-----------|-----------------------------------------------------------------------------|-------------------------------------------------------------------------|
| NET-001 | Must      | Каждое realtime-событие клиента имеет event ID, sequence и client timestamp | Server возвращает ACK с принятым ID и статусом                          |
| NET-002 | Must      | Неподтверждённые события сохраняются локально                               | Закрытие/перезапуск клиента до reconnect не теряет очередь              |
| NET-003 | Must      | После reconnect клиент повторяет события с теми же ID                       | Server дедуплицирует повтор и возвращает прежний результат              |
| NET-004 | Must      | Server учитывает согласованный clock offset                                 | Окно совпадения не сравнивает несинхронизированные wall clocks напрямую |
| NET-005 | Must      | Клиент видит accepted/pending/rejected                                      | Судья не принимает локальное нажатие за подтверждённый балл             |
| NET-006 | Must      | Сессия heartbeat обнаруживает разрыв                                        | Server и client переходят в disconnected за ограниченное время          |

## 13. История, аудит и отчётность

| ID      | Приоритет | Требование                                                        | Критерий приёмки                                                  |
|---------|-----------|-------------------------------------------------------------------|-------------------------------------------------------------------|
| AUD-001 | Must      | Журнал событий append-only                                        | Пользовательская операция не выполняет hard delete события        |
| AUD-002 | Must      | Коррекция ссылается на исходное событие                           | История показывает исходное и компенсирующее действия             |
| AUD-003 | Must      | История фильтруется по площадке, сетке, сессии, судье и типу      | Оператор может восстановить ход спорного результата               |
| AUD-004 | Must      | Время хранится с timezone/UTC и локальным представлением          | Экспорт однозначно интерпретирует timestamp                       |
| REP-001 | Must      | Экспорт XLSX содержит турнир, сетки, результаты и исходные оценки | Результат сверяется с UI и аудитом                                |
| REP-002 | Must      | Экспорт CSV доступен для машинной обработки                       | Формат, encoding и delimiter документированы                      |
| REP-003 | Must      | Экспорт формируется без интернета                                 | Файл создаётся на выбранном локальном пути                        |
| REP-004 | Must      | Экспорт имеет competition ID и время формирования                 | Два файла можно однозначно различить                              |
| BAK-001 | Must      | Автобэкап создаётся перед импортом                                | Ошибочный импорт не уничтожает предыдущую копию                   |
| BAK-002 | Must      | Автобэкап создаётся после завершения сессий                       | Последние результаты присутствуют минимум в одной отдельной копии |
| BAK-003 | Must      | Backup хранится до ручного удаления                               | Очистка требует подтверждения и не происходит по короткому TTL    |
| BAK-004 | Must      | Восстановление проверено тестом                                   | Новый/очищенный peer восстанавливает журнал и проекции            |

## 14. Нефункциональные требования

| ID      | Приоритет | Требование                                                    | Критерий приёмки                                                              |
|---------|-----------|---------------------------------------------------------------|-------------------------------------------------------------------------------|
| NFR-001 | Must      | Подтверждение локального клиентского события не блокирует UI  | Клиент показывает pending немедленно и обрабатывает ACK асинхронно            |
| NFR-002 | Must      | Здоровая LAN обеспечивает realtime-обновление                 | Pilot target: ACK p95 не более `200 мс`, UI update p95 не более `500 мс`      |
| NFR-003 | Must      | Потеря пакетов и reconnect не теряют события                  | Fault-injection тест показывает 0 потерянных и 0 повторно применённых событий |
| NFR-004 | Must      | Сервер восстанавливается после аварийного завершения          | Durable events и завершённые результаты не пропадают                          |
| NFR-005 | Must      | Секреты не хранятся в репозитории                             | Credentials и join secrets отсутствуют в tracked files и логах                |
| NFR-006 | Must      | Анонимные изменяющие HTTP-запросы запрещены                   | Аналог текущего открытого `POST /score` отсутствует в pilot contract          |
| NFR-007 | Must      | Входные payload имеют размер и schema limits                  | Невалидные/слишком большие запросы отклоняются до business logic              |
| NFR-008 | Must      | Логи структурированы и не содержат лишние персональные данные | Диагностика связывается по IDs, а не полным payload по умолчанию              |
| NFR-009 | Must      | Миграции PostgreSQL версионируются                            | Clean install и upgrade с предыдущей pilot schema проходят автоматически      |
| NFR-010 | Must      | PostgreSQL lifecycle управляется приложением                  | Start/stop/upgrade/ошибка порта обрабатываются на Windows и macOS             |
| NFR-011 | Must      | Критические формулы покрыты unit tests                        | Для каждой дисциплины есть нормативные примеры и boundary cases               |
| NFR-012 | Must      | API и realtime покрыты contract/integration tests             | Client/server несовместимость обнаруживается в CI                             |
| NFR-013 | Must      | P2P покрыт многопроцессным integration test                   | Проверяются join, sync, partition, restart и convergence                      |
| NFR-014 | Must      | UI пригоден для landscape/mobile и desktop-размеров пилота    | Реальные устройства проходят smoke-test без недоступных контролов             |
| NFR-015 | Should    | Интерактивные элементы имеют доступные подписи                | Screen reader/semantics test не находит безымянных критических кнопок         |

Значения latency являются pilot targets и уточняются после измерений на реальной сети, но не могут быть удалены без
замены измеримыми критериями.

## 16. Не входит в v1 Pilot

- генерация жеребьёвки и алгоритмы посева;
- передача активной сетки между площадками;
- централизованный cloud backend;
- обязательный доступ в интернет;
- публичная публикация в Google Play/App Store;
- Windows code signing и macOS notarization;
- автообновление приложений;
- полноценная учётная запись с паролем;
- видеоповтор как система записи/воспроизведения видео;
- Korean localization;
- `Кнопка самоуничтожения` из Figma.
