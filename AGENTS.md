# Правила работы с репозиторием

## Git и pull requests

1. Делите разработку на несколько небольших логических коммитов. Каждый коммит должен быть самостоятельным, понятным и проходить относящиеся к нему проверки.
2. Перед открытием pull request проверьте, что `README.md`, `docs/` и другие затронутые документы обновлены и точно отражают состояние после изменений.
3. После завершения работы и прохождения проверок открывайте pull request в целевую ветку. В описании PR укажите цель, ключевые изменения, проверки и известные ограничения.
4. Перед коммитом запускайте относящиеся к изменению Gradle-проверки, тесты и сборку; фиксируйте в PR выполненные команды и их результат.
5. Не коммитьте секреты, IDE-конфигурацию, локальные данные, каталоги сборки и generated artifacts, если их добавление не запрошено явно.
6. Не смешивайте в одном PR рефакторинг, изменение поведения и обновление зависимостей без явного обоснования в описании PR.
7. Используйте Conventional Commits: `<type>(<scope>): <imperative description>`, например `feat(pairing): add device approval flow`. Допустимые типы: `feat`, `fix`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`.
8. Заголовок PR оформляйте по шаблону `<Type> | <Imperative Description>` в Title Case, например `Feat | Enforce Java 21 Validation`. `Type` соответствует типу Conventional Commit с первой заглавной буквы.
9. Планируйте PR как инкремент поставки из раздела «Инкременты поставки» `docs/ROADMAP.md`: сценарий, воспроизводимый из production entry point (`./gradlew :desktop:run` или installer), который переводит хотя бы одно Must-требование в `Implemented` или закрывает пункт gate. Включайте все принадлежащие репозиторию слои сценария, включая wiring в `Server.start()`/desktop и UI; отдельная команда, transition, таблица, DTO, publisher или unit test является коммитом внутри инкремента, а не целью PR. Ориентир - 3-7 рабочих дней и одна issue; допускается 2-3 последовательных PR под одной issue, если каждый оставляет `main` рабочим. Большой инкремент делите по сценариям, а не по слоям. Для cross-repository сценария связывайте issue и PR обоих репозиториев и фиксируйте интеграционное/physical-device evidence.
10. Узкий PR допустим только для срочного исправления, явно блокирующей подготовки, изолированного CI/docs изменения или prerequisite, который нельзя проверить внутри инкремента. Issue и PR должны объяснять, почему сценарий нельзя включить сейчас, указывать родительский инкремент и следующую работу. Не отмечайте partial evidence как выполненный requirement или gate и не пишите для него отдельный narrative в документации.
11. Перед реализацией создавайте отдельную ветку от актуальной целевой ветки. Называйте её по шаблону `<type>/<short-kebab-scope>`, например `feat/device-pairing` или `fix/outbox-retry`; не выполняйте задачу напрямую в `main`.
12. После завершения инкремента обновляйте его строку в `docs/ROADMAP.md` и таблицу доказательств соответствующего этапа; это единственное место статусов requirement IDs. Отмечайте выполненные пункты roadmap Markdown-чекбоксом `- [x]`, а незавершённые оставляйте как `- [ ]`; requirement IDs, этапы и gates отмечайте только при наличии тестов или другого зафиксированного доказательства приёмки. `README.md` и `docs/PROJECT.md` содержат краткое текущее состояние без повторения доказательств.
13. Считайте локальный `main` актуальным. Перед созданием рабочей ветки переключайтесь на локальный `main`, но не выполняйте `git fetch`, `git pull` или другие сетевые Git-операции без явного запроса пользователя.
14. Для каждого PR сначала создавайте GitHub issue, связывайте её с подходящим milestone и указывайте связанные requirement IDs, scope и acceptance criteria.
15. В описание каждого PR добавляйте `Closes #<issue-number>`, например `Closes #20`, чтобы GitHub автоматически закрыл связанную issue после merge.
16. Перед созданием или обновлением issue и PR заполняйте GitHub metadata: назначайте `@TheGeniusOfEternity` assignee, подходящий milestone, один `type:*` label, релевантные `area:*` и `priority:*` labels, а для scope v1 - label `pilot`. Добавляйте issue и PR в подходящий GitHub Project; если Project не определён, спросите пользователя, а не создавайте новый самостоятельно.

## Skills

17. Project skills хранятся в `.claude/skills/` (Claude Code) и `.opencode/skills/` (OpenCode) с одинаковым содержанием. Изменяйте оба каталога в одном коммите.
